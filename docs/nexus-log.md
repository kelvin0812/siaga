# Nexus Log

AI collaboration record for the SIAGA build (Project Nexus 2026, Track 3). Kept per build brief Section 10.1: how AI shaped workflow and design, where the team caught and corrected an AI error or limitation, and how the AI-assisted result diverged from the original concept. Entries are dated and in build order.

## 2026-08-13 — Step 1: shared data contract + synthetic telemetry generator

**Gap found before writing code.** `CLAUDE.md` Section 8 ("Build Order") is a header with no actual numbered steps — just the instruction to follow a sequence that isn't written down. The working agreement in Section 1 explicitly requires flagging ambiguity rather than silently picking an interpretation, so this was raised to the team before any implementation started.

**How it was resolved.** Offered the team a choice of orderings inferred from other sections (2.2's stated importance order, 3.5's "build the simulator early," the physical data-flow order in Section 4). The team gave no preference, so the AI-recommended order was used: shared data contract + simulator → backend → app → firmware. This is a case where the brief's own stated priority (get the alerting path testable before hardware exists) is the deciding argument, not just AI judgment — worth revisiting if the team disagrees once the backend exists.

**What was built.**
- `shared/frame.py`: the 12-byte packed binary uplink frame codec (Section 5.1), including `level_mm_to_height_above_datum`, the single point where the down-looking-distance inversion happens. Kept as the one authoritative definition — the gateway firmware's C++ struct will need to be hand-mirrored against this, not the other way around.
- `shared/simulator.py`: a deterministic rising-hydrograph generator (`HydrographGenerator`) producing valid `UplinkFrame` sequences — smoothstep rise to peak, exponential recession, correlated rainfall/soil-moisture/tilt, and a simplified rate-of-rise check standing in for the node's real Tier 1 anomaly logic (Section 6.1) since reimplementing EWMA/z-score/autoencoder logic here would duplicate firmware work not yet done. A `replay_realtime(speed=...)` wrapper exists for later wiring into the backend's MQTT publisher.
- 31 pytest tests across `tests/test_frame.py` and `tests/test_simulator.py`, covering round-trip encode/decode, all field boundary values, the flags-byte bit layout including the two-bit boot-cause subfield, and — the case Section 5.1 calls out as the most likely bug source — that rising water produces a *decreasing* `level_mm` and a correctly increasing computed height.

**Assumption made, flagged for the team to confirm or override:** the anomaly-flag rate-of-rise threshold in the simulator (`anomaly_rate_mm_per_min`, default 30 mm/min) is a placeholder chosen to make the demo hydrograph exercise the flag, not a hydrologically-derived value. Section 6.1 asks for "an explicit rate-of-rise threshold from hydrological first principles" on the real node — that derivation still needs to happen and this number should not be treated as it.

**Divergence from the original concept:** none yet at this scope — this step is infrastructure (codec + fixture) rather than a design decision with room to diverge.

## 2026-08-14 — Step 2: backend

**Two conflicts with the fixed brief, raised before writing any backend code.** The team asked for Supabase and Vercel deployment. Supabase is Postgres, and Section 4.1 says explicitly "do not introduce Postgres for a 3-node demo." Separately, Section 6.3 requires an always-connected async MQTT subscriber, and Vercel functions are stateless and time-limited — they cannot hold that connection. Both were surfaced to the team rather than silently worked around.

**Resolution (team decision, no preference expressed beyond "proceed"):** Supabase override, logged here and annotated in `backend/schema.sql`. Deployment split in two: an always-on process (`backend/app/main.py`, containerized via `Dockerfile`) runs the MQTT ingest loop, guardrail, state machine, and FCM dispatch — this is still exactly the brief's "single process," just not the process Vercel hosts. A separate read/write-only REST API (`api/index.py`) serves Section 5.3's endpoints from Vercel, reading the same Supabase database. The state machine only ever runs inside the persistent process, never on Vercel, so there's no cross-instance state problem.

**A second undocumented gap, found while designing `/api/v1/density`:** Firebase Cloud Messaging has no API to read a topic's subscriber count. Section 3.1 assumes that number exists; nothing in the brief says how. Resolved by adding `POST /api/v1/subscriptions/ping` (cell_id + delta, no device identifier) — not in Section 5.3's "fixed interfaces" table, so flagged rather than added silently. `cell_subscriptions` in `backend/schema.sql` backs it.

**An AI-introduced bug caught during testing, not before it.** `backend/demo.py`'s first version stamped every replayed reading with `datetime.now()` (real wall-clock time) instead of the simulator's own simulated timestamps. At fast-forward playback speeds this collapsed the time delta between consecutive readings toward zero, which silently corrupts `features.py`'s rate-of-rise calculation and would have made every dwell timer in the state machine behave unpredictably. It wasn't caught by unit tests — `test_pipeline.py`'s hydrograph test already used correct simulated timestamps, so it passed while the demo script itself was wrong. It was caught by actually running `python -m backend.demo` and noticing the replay ended at NORMAL with zero logged transitions, which shouldn't happen given a hydrograph designed to trip the anomaly threshold. Root-caused with an ad hoc debug script comparing simulated-time vs. wall-clock-time playback side by side, then fixed. This is exactly the class of error Section 10.1 asks this log to record: a plausible-looking implementation that was wrong in a way only running it — not reading it — revealed.

**Assumptions made, flagged for the team to confirm or override:**
- Guardrail corroboration thresholds (tilt >= 3.0°, soil >= 85%, rain >= 20mm/1h in `backend/app/guardrail.py`) are prototype defaults, not calibrated against any real catchment.
- State machine de-escalation dwell (30 minutes, `state_machine.py`) is this implementation's choice, not a brief-given value — the brief only fixes WARNING's 10-minute escalation dwell and says de-escalation must be longer.
- Per-node `critical_height_m` (the EVACUATE physical-breach threshold) and `datum_mm` are new columns on `nodes`, since Section 5.1's height conversion and Section 5.4's absolute-threshold guardrail both need site-specific calibration the brief doesn't otherwise provide a home for.
- Tier 2 is a heuristic stub (`backend/app/tier2.py`), not the LightGBM model Section 7 specifies — that requires historical training data acquisition, which is separate future work, not part of wiring the backend together.

**Divergence from the original concept:** the two-service deployment topology (persistent ingest host + Vercel API) is a real architectural divergence from Section 4.1's single-process description, driven entirely by the team's Supabase/Vercel request rather than by anything in the original proposal.

## 2026-08-14 — Supabase provisioning

Given direct Supabase access to apply the schema. The account's one existing project turned out to already hold an unrelated app's tables (`pantry_sync`: inventory, fridge_status, sensor_log, inventory_log) — this was caught by listing tables before running any DDL, not assumed. Flagged to the team rather than either reusing that project silently or guessing; the team chose a new dedicated project (`siaga`, ap-southeast-1/Singapore — closer to the Malaysian catchments this system targets than the existing project's Tokyo region).

`backend/schema.sql` applied as a migration. Supabase's advisor tooling immediately flagged all 7 tables as ERROR-level: Row Level Security disabled, meaning the project's anon key could read/write every row via Supabase's REST API. Nothing in Section 5 anticipates this — the brief designs the REST API surface (Section 5.3) and the k-anonymity threshold (Section 3.1) assuming the backend is the only thing touching the database, but never states that Supabase's own auto-generated API needs to be locked down separately. Surfaced to the team with the exact remediation SQL before applying it (enabling RLS blind, with no policies, can silently break legitimate access if something *does* need anon-key access later). Team confirmed enable-with-no-policies. Re-ran the advisor after — confirmed only the expected informational "RLS enabled, no policy" notices remain, no ERROR-level findings. This is safe specifically because the backend connects with its own Postgres connection string (table owner, bypasses RLS) rather than through PostgREST — if the Flutter app is ever changed to talk to Supabase directly instead of through the FastAPI REST API, this decision needs revisiting.

## 2026-08-14 — Vercel provisioning

Vercel project creation initially failed with a 403 across both the git-linked path and the direct file-upload path — the MCP connector's authorized token didn't include project-creation scope. Reported this plainly rather than retrying blindly, since repeated identical calls against a permissions error wastes effort without new information. Team reconnected the connector; project creation then succeeded (`siaga`, prj_QUd5uBepggMYQJ7sbJ3jPoNbCZlq, linked to kelvin0812/siaga). Immediately after, read endpoints (list_projects, get_project, list_deployments) returned empty/404/403 — inconsistent with the project actually existing. Confirmed the project was real (not a phantom success message) by re-issuing create_git_project and getting a 409 conflict rather than another success, which only happens if Vercel's server already has the project. Treated this as a propagation-lag/scope-sync issue on the read side rather than assuming the write had silently failed, and proceeded via the path that doesn't need those reads: the project is git-linked, so pushing to GitHub triggers a deployment regardless of whether the MCP connector can currently list it.

First deployment verified live by fetching `/api/v1/health` directly (browser) rather than trusting an unreadable MCP deployment status — got a correct FastAPI JSON response with `total_nodes: 0`, confirming the app was running against the InMemoryRepository fallback (no `DATABASE_URL` configured on Vercel yet at that point), not a build failure. Also fixed `db_postgres.py` to pass `statement_cache_size=0` to asyncpg's pool — Supabase's connection pooler (required for serverless, since a pool of direct Postgres connections doesn't scale against Vercel's concurrent-instance model) runs PgBouncer in transaction mode, which is incompatible with asyncpg's default prepared-statement caching. Team then set `DATABASE_URL` (Session pooler string) in Vercel's environment variables manually, since no MCP tool in this connector exposes environment-variable management at all.

`total_nodes: 0` alone couldn't distinguish "connected to Supabase but empty" from "still on the in-memory fallback," so verification wasn't treated as complete until a stronger test: inserted a row directly via Supabase, confirmed it appeared through the live Vercel API, then deleted it. Accepting a weaker signal (an OK-looking empty response) as proof would have been the kind of silent-pass mistake worth avoiding.

## 2026-08-14 — Step 3 scope change: web app instead of Flutter

Team asked for a website instead of the Flutter app Section 4.1 fixes as a technology choice and Section 6.4 builds specific requirements against. Flagged before starting: Section 6.4's "full-screen high-priority presentation for EVACUATE" is a native-OS notification-channel capability that the web doesn't have an equivalent for, and it's substantially weaker on iOS Safari specifically (web push there requires the site be installed to the home screen as a PWA; a plain browser tab gets nothing at all). The rest of Section 6.4 — offline caching, on-device H3 computation, FCM topic subscription, multilingual templating — translates to a PWA without meaningful loss.

Team chose to proceed with web anyway (no preference on the native-parity question beyond "recommended"), stack: Next.js PWA on Vercel, alongside the existing backend deployment. Logged as a deliberate override, same class of decision as the Supabase/Vercel choice — the EVACUATE alert-reliability gap versus native is real and should be re-examined if the team pursues this beyond the competition.

**Reversed minutes later, before any app code was written.** A Next.js project had been scaffolded (`npx create-next-app`) and dependencies installed when the team reconsidered and asked to go back to Flutter — specifically because of the EVACUATE alert-reliability gap flagged above. This is the web-vs-native tradeoff resolving the other way once it was concrete rather than hypothetical; the scaffold was removed (no committed code existed yet, so nothing to revert in git) and Section 4.1/6.4's original Flutter plan resumed. Recorded here because Section 10.1 asks for how the AI-assisted result diverged from the original concept, and "the team explored an alternative, then reverted after weighing the real tradeoff" is exactly that, even though the reversal wasn't a correction of an AI mistake.

## 2026-08-14 — Step 3: Flutter app

Built `app/`: on-device H3 computation + FCM topic subscription (Section 3.1's privacy core), a live map with node history charts, the "My Risk" indicator, hazard reporting, BM/EN localization, offline caching, and a demo mode — Section 6.4's full list, on Flutter/Android+iOS as originally specified.

**A real, environment-specific gap found before writing any test:** `h3_flutter`'s native binding can't load under `flutter test` on this Windows machine — there's no bundled host-platform binary; it's compiled from source as part of a full `flutter build windows`, which unit tests don't run. Rather than leave `H3Service` untested or skip testing the location logic built on top of it, added a narrow `CellComputer` interface so `LocationService`'s cell-boundary-crossing logic — the part with actual behavior worth testing — could be exercised with a fake, independent of the native binding. `H3Service` itself stays untested in this environment; that's a known, explained gap, not a silent one.

**Two real bugs found by actually running the app, not by reading the code:**
1. `main.dart`'s startup sequenced `await locationService.requestPermissionAndStart()` before `await appState.refresh()`. In a browser with no one present to click the geolocation permission prompt, that first await hangs indefinitely — confirmed by checking network requests in the running preview and seeing zero calls to the backend at all, ever, not even a failed one. Fixed by making location permission and data refresh run independently (`unawaited(...)` for the former), since Section 6.4's live map/node list must work regardless of whether the user grants location. This is exactly the class of bug Section 10.1 asks this log to record: invisible from reading the code, only found by running it and asking "why is nothing happening."
2. CORS: the deployed backend has no CORS headers, so a browser-based client can't call it at all (native Android/iOS HTTP clients don't enforce CORS, so this never would have surfaced testing only on-device — it was only visible because the local dev-preview convenience happens to be a browser). Added `CORSMiddleware` with a wildcard origin to `backend/app/main.py` — safe here specifically because Section 11 confirms no auth model exists anywhere in the system, so there's no session/cookie exposure a wildcard origin would create.

**A gap in the brief itself, found while building the report form and the EVACUATE screen:** Section 5.3's `ReportIn.photo_url` assumes a photo gets uploaded "somewhere" first, and Section 6.4's "cache evacuation routes, assembly points" assumes a data source for them — neither is specified anywhere, and no object-storage or routing backend exists in this project. Rather than build a half-working photo picker with nowhere to send the file, or fake turn-by-turn routing with no routing API, both were scoped down honestly: photo attachment is deferred (report form ships fully functional for category/note/cell_id), and assembly points are a small bundled static asset with straight-line distance/bearing to the nearest one — good enough to point someone in the right direction for a demo, explicitly not a substitute for official guidance (which the alert copy itself already says).

**Assumptions flagged for the team to confirm:** the demo mode's depth-to-risk-state mapping (`DemoController._stateForDepth`) is a simplified illustrative threshold, not a client-side reimplementation of the backend's real dwell/hysteresis state machine — deliberately, so there's only one place (`state_machine.py`) that can drift from the spec. The EVACUATE full-screen takeover is a Flutter full-screen dialog route, the closest a foreground app screen can get to Section 6.4's "full-screen high-priority presentation" — it is not a system-level notification-channel takeover (no foreground service / full-screen-intent wiring), which only matters when the app isn't already open; that gap was the whole reason the team almost went with web instead and is worth revisiting if EVACUATE delivery reliability becomes a real concern.

**A verification-tooling limitation, handled by switching methods rather than lowering the bar.** The local browser preview used to develop this (Flutter's web target, run only as a dev convenience — Section 4.1 still fixes Android/iOS as the shipped platforms) stopped compositing frames partway through this session for reasons outside the app: screenshots failed, and `WidgetsBinding.addPostFrameCallback` — which only fires after a real rendered frame — silently never ran, so the startup-concurrency bug fix above couldn't be confirmed by watching the browser. Rather than accept "no errors in the console" as sufficient proof, wrote `test/startup_concurrency_test.dart`: a real `flutter_test` widget test that pumps the actual `SiagaApp` with a `LocationService` whose permission future never resolves (reproducing the hung-prompt scenario exactly) and a mocked HTTP client. Confirmed the test fails without the fix and passes with it before trusting either. `flutter_test`'s frame pumping is deterministic and doesn't depend on real browser compositing, so this is arguably a more reliable check than the browser preview would have been anyway.

## 2026-08-14 — Team feedback pass on the Flutter app

Team asked for four UI changes after using the app: a visible "my location" marker on the map, visible risk-indicator behavior, a more polished report form, and a fuller settings screen. Two of these turned out to have a real bug underneath, not just a cosmetic gap:

**The risk indicator complaint was a real bug, not a missing feature.** Demo mode's hazard `cells` list was populated from `AppState.currentCellId`, which comes from real GPS — but the whole point of demo mode is running at a booth with no GPS fix needed. With no location permission granted (the default in a browser, and plausible at a booth too), `currentCellId` stays null forever, so every demo hazard shipped with an empty `cells` list, and the "My Risk" indicator could never leave NORMAL no matter what the demo hydrograph was doing. Fixed at the root: `AppState.myRiskState` now reads the demo node's state directly when `demoMode` is true, instead of going through cell-matching logic that demo mode was never able to satisfy. `RiskScreen`'s hazard-message lookup had the identical bug and got the identical fix. Regression-tested (`app_state_test.dart`: demo mode reflects the node state with no GPS fix at all).

**The map and report requests were genuine feature gaps**, not bugs: added a distinct pulsing "my location" marker (`LocationService.positionUpdates`, a new stream separate from the existing cell-change stream, since the marker needs to track smoothly rather than jump only on H3 boundary crossings — still device-local only, same boundary as `lastKnownPosition`) with a tap-through info sheet; replaced the report form's radio-button category picker with a dropdown and added a free-text "where did you notice this" field, folded into the existing `note` payload on submit rather than inventing a new backend field Section 5.3 doesn't have room for.

**Settings needed a service that wasn't in the provider tree.** `FcmService` was constructed in `main()` and passed directly to `SiagaApp`'s constructor, but never registered with `provider` — fine until the new notifications section needed `context.read<FcmService>()` from a screen three levels down. Added it to the `MultiProvider` list (and to `startup_concurrency_test.dart`'s test harness, which pumps the same widget tree and would otherwise throw a `ProviderNotFoundException` the moment `SettingsScreen` builds inside the `IndexedStack`).

## 2026-08-14 — Second feedback pass: node detail as an overlay, demo control

Team asked for two more things: node history shouldn't require navigating away from the map (map and analysis should be visible together), and demo mode needed to show actual sensor numbers plus a way to trigger a high-risk state on demand for live demos.

**Replaced `Navigator.push` to a separate `NodeDetailScreen` with a `DraggableScrollableSheet` overlay** in the same `Stack` as the map — tapping a node marker now opens a panel that can be dragged between minimized and expanded, map still visible and interactive above/behind it. Extracted the chart-fetching logic into a standalone `NodeHistoryChart` widget (no `Scaffold`/`AppBar`) so it can be embedded instead of requiring a full page; `node_detail_screen.dart` had no remaining references afterward and was deleted rather than left as dead code.

**Extended the demo generator with fields it didn't have before** (`tempC`, `rhPct`, `vbatVolts`, `rainTips` on `SimulatedPoint`) so the demo panel can show an actual sensor readout, not just a colour badge. Deliberately did NOT add a "pressure" field despite it being requested casually in conversation — Section 5.1's wire frame only ever carries `temp_c` and `rh_pct`, no barometric pressure field exists anywhere in the real data contract even though the BME280 hardware can sense it, so fabricating one in the demo would show data the real system can never actually produce. Flagged this rather than silently adding a plausible-looking fake field.

**Added `DemoController.jumpTo(RiskState)`** for instant manual triggering from Settings (four buttons: Normal/Watch/Warning/Evacuate), for live demos where waiting through the automatic hydrograph timer isn't practical. Implemented by searching the already-generated point list for one that lands in the target state, rather than fabricating separate synthetic sensor values for each button — keeps the manually-triggered readout internally consistent with the same hydrograph the automatic run uses. `jumpTo` stops automatic playback rather than letting the next scheduled tick silently overwrite the manual choice; tested that a manual jump survives elapsed time with the timer stopped, and that all four states are reachable from the default config.

## 2026-08-14 — Third feedback pass: real sensor list, hardware BOM mismatch surfaced

Team specified the sensors actually being sourced for the physical build: capacitive soil moisture, a gravity analog water pressure sensor, a radar water depth sensor, and the MPU6050 IMU. Asked for the demo readout to show exactly these, plus the node's GPS coordinates, plus removing the debug banner.

**Surfaced a hardware BOM mismatch rather than silently absorbing it.** Section 2.1's hardware list and Section 5.1's 12-byte wire frame were both built around a JSN-SR04T ultrasonic level sensor and a BME280 (temp/humidity/pressure, but only temp_c and rh_pct actually get transmitted) — no independent water-pressure sensor exists anywhere in that design. The team's actual sensor list swaps in a radar depth sensor (functionally interchangeable with the ultrasonic one — still just "distance to water surface," no frame change needed) but adds a genuinely new sensor type, water pressure, that Section 5.1 has no field for at all. This only affects the demo UI so far — the real backend, REST API, and wire frame are all untouched — but it's a live discrepancy between the brief's fixed hardware section and what's actually being built, and it'll need reconciling in the node firmware and frame codec once that work starts, not just here.

**Kept the demo's water pressure honest rather than fabricated.** Computed `DemoReading.pressureKpa` as a getter derived from depth via real hydrostatic physics (kPa = depth_m × 9.81), not as an independently-simulated value — a pressure sensor at the base of a water column genuinely would read something close to this, so it's a legitimate derivation, unlike the earlier-refused "barometric pressure" request which had no physical relationship to anything the system models.

**Trimmed the demo readout to exactly four fields** (soil moisture, water pressure, water depth, tilt/"soil inertia" in degrees) matching the team's real sensor list, removing temperature/humidity/rain-tips/battery from the display — those fields still exist on `DemoReading` and are still computed (harmless, and match Section 5.1's real frame), just no longer rendered, since nothing in this request said to touch the underlying simulation or the real data contract.

**Added the node's GPS coordinates to the map panel** — this is the sensor *node's* fixed public install location (already part of Section 5.3's `/nodes` response), not a user's handset location, so Section 3.1's constraint doesn't apply here at all; no privacy concern in showing it. Also removed the debug-mode banner (`debugShowCheckedModeBanner: false`) — purely cosmetic, no effect on release builds either way.
